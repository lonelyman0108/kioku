# 0001. 以记忆圈与透镜访问密钥取代孤岛空间与多层归属

- 状态：生效（2026-11-18）
- 日期：2026-11-18

## 背景

原有架构以物理隔离的「空间（Space）」作为唯一边界，在空间内部再嵌套「通用 / 人格 / 应用 / 本人 / 联系人 / 会话」六类归属。随着使用场景扩展，这套模型暴露出三处限制：
1. 个人需要在家里电脑、公司电脑、个人项目、家庭共享与公司团队之间交叉使用记忆，物理孤岛导致通用偏好与经验无法随人流动；
2. 把 `app`（应用）同时作为词条归属与访问凭据载体，导致多台电脑与多种工具产生 `M × N` 碎片化，同机工具间共享环境配置困难，且 `app://` 无法跨运行时复用；
3. 将聊天机器人接入多群与私聊时，需要区分「全新独立记忆」与「挂载本人个人圈只读」，同时需要允许密钥轮换不丢失按群人格规则与会话关联，并在「拟人跨群识人」与「严格按群隔离」间可配置切换。

## 决策

1. **顶层改以「记忆圈（Circle）」组织**：每个账号创建时自带唯一不可删的**个人圈**（存放私人记忆、随身偏好、含凭据占位符的私密词条及涉公/涉家私下记录），并可新建或加入多个**共享圈**（家庭圈、公司圈、机器人社交圈等；保留 `owner` / `editor` / `viewer` 三角色与离开 30 天保留期）。共享圈内的正式词条（`kind = 'entry'`）全部为圈内共享（`owner_account_id IS NULL`），彻底废除旧版 `user://` 在团队空间内混放成员私密正式词条的模式。数据库内容表全部改由 `withCircles(db, { read, write }, fn)` 事务分别设置会话变量 `app.read_circles` 与 `app.write_circles`，按 `SELECT` 与 `INSERT` / `UPDATE` / `DELETE` 建立四条分命令 PostgreSQL 行级安全（RLS）策略：读与生命周期请求可传入多个可读客场圈但 `write` 严格锁在主场圈（或明确有写权限的目标圈），既允许主场圈正常写入新联系人、活跃时间与召回事件，又从数据库层物理阻断对只读客场圈的 `UPDATE` 与 `DELETE`。
2. **剥离词条归属层，保留轻量接入实例**：取消词条上的 `app://` 与 `persona://` 归属层——客户端适用性改由内置 `runtime` 切面表达，人格独立为纯灵魂与口吻模块（按 `trait_key` 继承覆盖）。同时在接入管理层保留轻量的**接入实例（`clients`）与按群规则（`client_group_rules`）**，专门承载所属圈、所有者、默认人格、按群人格覆盖、单群隔离锁（`isolateGroupMemory`）、本人私聊提权与 `personMemoryMode`（`persona_shared` 拟人跨群识人 / `strict` 严格按群隔离）。访问密钥挂在接入实例之下，其主场圈与所有者统一继承自 `clients`，密钥轮换不断群规则与历史会话。
3. **透镜访问密钥与硬边界封顶**：每个访问密钥沿用所属 `clients` 的主场圈，并可绑定多个同账号所属关联客场圈（`read` / `read_write`）、终端在场切面 `context_facets` 与静态授权场域白名单 `scopes.allowedRealms`。多圈权限按每个圈独立计算 `CircleGrant`：所有者在主场圈失效或离开重进则该访问密钥整体作废；在某客场圈离开重进时自动剥离该客场圈视野，被降为 `viewer` 时强制收紧为该圈只读。服务端 JS 与 SQL 同步强制执行「有效权限 = 透镜上限 ∩ 会话上下文封顶」：严格区分**静态双向场域锁（既检密钥白名单 `scopes.allowedRealms`，也在 `allowedRealms` 为空时核对目标显式 `realms` 与密钥静态 `context_facets` 展开场域 $R_{\text{ctx}}$ 的交集；两者均绝不随请求 `project` 或提问触发词放宽，且机密词条下禁止挂载异场域切片）**与**动态存在感焦点**；本机无上下文请求允许普通记忆跨客场圈或异场域破壁读取，**机密词条（`secret`）与全部凭据（`{{cred:...}}`）在客场圈及未通过静态场域校验时一律返回 404**；群聊与外人私聊最高敏感级死锁为 `public`，本人私聊开启提权后放宽至 `internal`。

## 后果

- 个人记忆与个人凭据可跨场景安全随行且不污染团队或社交圈，半受信终端与公开群聊在数据库读写两端被硬边界锁死，密钥轮换不再破坏机器人配置。
- `withSpace` 需升级为支持读写分离双变量 RLS 的 `withCircles`，所有访问控制一致性测试（JS `canRead` 与 SQL `readableConditions`）需同步按新模型与多圈角色收紧逻辑重写。
- 需要提供确定性迁入工具，将原有 `Space` 内共享记忆迁入对应共享圈、将 `user://` 个人记忆拆分迁入各自账号的个人圈，旧 `apps` 转化为 `clients` 与 `runtime` 切面。

## 可推翻条件

若未来需要支持跨账号联合授权客场圈或针对外部协作者细化子圈角色权限，只需在透镜解析与 `withCircles` 鉴权层增加跨成员委派规则，无需推翻核心圈子模型。
