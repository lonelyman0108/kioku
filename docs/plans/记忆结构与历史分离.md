# 记忆结构规范化与历史变更分离计划（Kioku）

> 状态：进行中　　开始：2026-11-26　　负责人：维护者 / agent
> 全部完成后，文件头改为「已完成 YYYY-MM-DD」，用 `git mv` 移到 `docs/archive/plans/`。

面向 Kioku 单人自托管 12 张扁平表架构（[ADR-0004](../adr/0004-flat-single-owner-v2.md)），系统解决四类核心问题：

1. **标题膨胀与日志化**：Agent 四大核心读取入口（`boot`、`recall`、`kioku_browse`、`kioku_get` 文本输出）未暴露更新时间和最近变更摘要，叠加历史导入残留的首行重复 `# H1` 与宽松长度上限，倒逼 Agent 把日期与更新日志持续塞进 `title`。
2. **现行真相与变更历史混写**：底层虽有 `entry_events` 全量快照表，但无语义化变更说明且未对 Agent 开放；正文长期堆积过时流程与历次流水账，击穿启动加载字数预算（尤其在 9,500 字上限的宿主客户端下造成级联挤出，且 `omitted` 仅暴露裸短 ID），同时稀释单向量语义与 BM25 全文召回精度。
3. **跨条目关联语境与长文按需读取不足**：`entry_links` 当前仅记录无语义边，长篇架构/规范文档无法按 `##` 小节直取，`kioku_update` 缺少局部补丁能力导致长文更新易出现“只增不减”或“短补丁覆盖原文主体”。
4. **存量旧数据（含 Lore 导入残留）平滑换代**：提供零风险、可预览、全量可回滚的确定性预清洗 + 后台整理审阅迁新闭环，将存量脏标题、重复首行 H1、残留旧路径链接与正文流水账统一升级至新版结构。

**架构红线**：严格保持 **12 张扁平表、无 RLS、自由 Markdown**（不引入三元组图谱、不拆多态 JSON Schema、不新增顶级导航）；所有表结构改动为 `0000_baseline` 之后的纯增量可空迁移；保持与 `kioku-plugins`（`/v1/lifecycle/event`、`/v1/boot`、`/v1/recall`、`/v1/whoami`、`/v1/credentials/resolve`）及 `access/scope.ts` JS/SQL 双重权限边界 100% 向后兼容；不重新引入复杂的 token 预算手工设置页。

## 决策摘要

| # | 决策 | 采纳 | 可推翻条件 |
|---|---|---|---|
| 1 | 数据模型哲学 | **信封强结构、信纸自由化**：保持 12 张扁平表与自由 Markdown，不拆三元组图谱、不搞重型多态 JSON Schema | 未来演进为多人协作结构化资产库或需确定性多跳图谱引擎 |
| 2 | 词条结构增强 | `entries` 纯增量 3 个可空列：`summary`（≤300 字现行结论，与 `disclosure` 触发场景严格正交）、`verified_at`（事实核实时间）、`last_change_summary`（最新变更缓存）；不新增互斥 `entry_type` 枚举 | 未来出现强依赖条目类型驱动的独立业务流 |
| 3 | 状态与历史分离 | 激活升级现有 `entry_events`（增量 `change_summary`、`diff_meta`、`occurred_at`，扩展 `event_type = 'archive_note'`）；正文仅留现行真相与防踩坑原因（Rationale），过时流水账（Changelog）沉入历史；超长独立复盘用非常驻双链词条承载 | 变更历史需要独立于快照进行高频手工编排或全文检索 |
| 4 | 启动加载防挤出 | 不增加复杂 token 预算手工配置；保持现有字符硬上限，升级为**两遍渐进式 Boot**：Pass 1 为全部命中常驻预留带 `summary`/近改的紧凑目录槽（彻底消灭裸短 ID `omitted` 盲盒），Pass 2 按精准度与短篇优先原地展开全文；展示层自动去重首行重复 `# H1` | 宿主客户端上下文上限差异扩大到需要用户手工逐条指定 `pin_mode` |
| 5 | 关联与正文阅读补强 | `entry_links` 增量 `relation` / `context_snippet`（支持 `[[m-xxxxxx\|语境]]` 与行内上下文提取）；正文靠 Markdown 软骨架约定，配合 `kioku_get(view="outline", section="...")` 按 `##` 小节直取 | 需要跨条目外键级联更新或强字段校验 |
| 6 | Agent 历史与写入契约 | MCP 工具 8 → 9，新增只读 `kioku_history`（严格走 `readableEntrySql` 权限边界）；`kioku_update` 支持复用 `applyCapturePatch` 的局部 `patch` 与半强制 `change_summary`；新写入标题硬上限收紧至 80 字（存量未改标题的更新向后兼容），超 32 字或含日期日志返回非阻断 `warnings` | 实测软提醒在多模型下遵从率过低，需对新建标题提高硬门控 |
| 7 | 检索与向量加权 | `entries.fts` 升级为 PostgreSQL `setweight`（`title` A / `summary+disclosure+search_tags` B / `content` C）并利用 `unnest(fts).weights` 实现真 BM25F；`buildEmbeddingText` 改为结构化高信噪比拼接（去重复 H1、截断前 2,500 字、跳过尾部残留日志段），保持单向量表结构 | 单条核心参考正文在剥离历史后仍普遍超过 6,000 字且尾部召回不足 |
| 8 | 存量旧数据迁新 | 采用「确定性零误差预清洗（去重复 H1 / 清残留关键词行 / 断链映射复活 / 异常与过时标注）+ Dream `tidy` 分批进 `/inbox` 人工审阅（完整原文留快照 + 旧日期写 `archive_note` + 纯标题速审表 + 8 秒撤销）」；严禁直接写脚本盲改生产库 | 存量条目规模达到数千条以上无法人工抽审 |

长期有效的架构取舍如涉及对 [ADR-0004](../adr/0004-flat-single-owner-v2.md) 的增量说明，在阶段 7 同步更新 `docs/design.md`（必要时补写 ADR）。

### U01　备份线上数据库并升级实例镜像

- **在哪**：自托管部署主机（生产实例所在目录与容器编排平台）
- **操作**：
  1. 升级前使用 `pg_dump` 导出完整数据库快照并确认备份文件非空；
  2. 将服务端镜像切换至包含本计划全部改动的新版本（或 `edge` 镜像）并重启服务，确认增量迁移 `0001` 自动执行成功。
- **验证**：访问 `/v1/health` 返回 200；登录管理界面确认既有记忆、凭据、访问密钥均正常展示，启动加载不再出现裸短 ID 挤出。
- **回滚**：停止新版容器，切回旧版镜像标签，并以升级前 `pg_dump` 备份恢复数据库。
- **告诉 agent**：「生产实例已备份并升级至新版，健康检查正常。」

### U02　执行存量确定性预清洗与分批 `/inbox` 审阅

- **在哪**：管理界面「记忆」与「待处理」（`/inbox`）页面
- **操作**：
  1. 先运行存量体检预览（Dry-run），复核确定性预清洗清单（重复首行 H1、残留关键词行、旧路径断链映射），确认无误后应用；
  2. 核对被标红的异常残缺条目（正文被单次短补丁覆盖的旧条目）与已淘汰旧阶段项目条目（决定保留、合并或移入回收站）；
  3. 按 3 批触发规范整理（第 1 批：常驻记忆 → 第 2 批：纯标题规范速审表批量应用 → 第 3 批：其余含历史流水账的按需记忆），在 `/inbox` 核对完整性护栏与 Diff 后逐批应用。
- **验证**：常驻记忆启动加载总字数明显回落且全部可见；待处理页规范整理建议清零；任意抽查 2–3 条已清洗记忆的「版本历史」，确认原有完整快照与剥离出的历史说明均可查阅与恢复。
- **回滚**：单条不满意可在该记忆的「版本历史」一键恢复至清洗前快照；大范围回退可使用 U01 的数据库备份。
- **告诉 agent**：「存量三批清洗已在待处理页审阅完成。」

### U03　触发全量向量补齐与线上实测复核

- **在哪**：管理界面「设置 › 模型」与常用 Coding Agent 会话
- **操作**：在「设置 › 模型」点击向量重建/补齐，等待向量覆盖率达到 100%；新开一次 Coding Agent 会话确认启动加载与每轮召回效果。
- **验证**：向量覆盖率 100%；启动加载无重复标题、无裸短 ID、含更新时间与近期变更说明；召回不再被已退场的过时项目记录霸榜。
- **回滚**：无需回滚（向量重建仅刷新衍生索引）。
- **告诉 agent**：「向量重建完成，新会话验证通过，可以归档本计划。」
