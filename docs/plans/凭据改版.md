## 决策摘要

## 做法

- 第 0 期是文档 PR，维护者审过再合并。设计文档写改版后的规则，文件头注明实现完成之前代码仍是旧规则；`AGENTS.md` 写的是代码现在的行为，跟着代码改。
- 第 1 期同时改契约、库结构、服务与界面，中间状态编译不过，所以在集成分支 `feat/credential-redesign` 上做，完成后整体开 PR，按 high 级审查。拆给三个 subagent 并行，实现用的 subagent 一律设 `effort: medium`（维护者 2026-11-07 要求）：
  - Bitwarden 客户端：独立模块，只用 `node:crypto` 与 `fetch`，不碰库。
  - 契约、库结构、凭据服务与 MCP。
  - 管理界面：等契约定下来再开始。
  - 各自用自己的 worktree、集成测试库与走查端口，不改计划与设计文档；主 agent 审查后合回集成分支。
- 第 2 期跨两个仓库：Kioku 的取值接口先合并，插件仓库再做 `kioku run`。第 3、4 期各开一个 PR，改动大时也走集成分支。
- 测试：
  - Bitwarden 的固定数据：在本地起一个 Vaultwarden 容器，用官方 bw CLI 写入条目后导出，存进仓库（都是测试账号，没有真实数据）。CI 只跑用这些数据的单元测试。
  - 真连 Vaultwarden 的集成测试按环境变量 `KIOKU_TEST_VAULTWARDEN_URL` 开关，在本地跑（`docker-compose.dev.yml` 加一个 Vaultwarden 服务）。要在 CI 里也跑，另开一个改工作流的 PR，由维护者审（禁区）。
  - 写回（第 4 期）用 bw CLI 读回 Kioku 写的条目来核对。
- 新目录 `apps/server/src/credential/bitwarden/` 在已有的 `credential` 下，不算新的顶层目录，在 PR 里说明。

- **操作**：
  1. 建一个组织（例如「Kioku」）和一个集合（例如「Agent」）。

### 1 · 服务端取值

- [x] Bitwarden 客户端（`credential/bitwarden/`）：
  - 密钥派生：预登录取 KDF 参数，按 PBKDF2-SHA256 或 Argon2id 派生（Argon2id 加一个依赖，版本写死）。
  - 登录：主密码登录，开了两步验证时带验证码，之后用刷新令牌换访问令牌。
  - 取条目：同步列出条目，按 id 取单个条目。
  - 解密：AES-256-CBC 加 HMAC-SHA256（先校验 MAC），RSA-OAEP 解组织密钥，条目自己的密钥；不认识的加密格式明确报错。
  - 错误信息不带密钥、令牌与响应正文，照 `fetchFailure`、`upstreamJson` 的做法。
  - 测试：单元测试用固定数据，集成测试连本地 Vaultwarden。
- [x] 契约与库结构（新迁移）：

## 以后再做

不在这六期里，记下来以免丢：

- 卡片、身份与 SSH 密钥条目的专有字段：现在只取备注与自定义字段。SSH 私钥对 agent 有用，优先做。
- 邮件两步验证：要先调接口请求服务端发送验证码。
- 官方服务（bitwarden.com）上没验证过的假设：`client_id` 用 cli、新设备验证、刷新令牌会轮换、看不到的条目返回什么。测试只在 Vaultwarden 上做过。
- Vaultwarden 的「访问全部集合」在账号资料里看不到，组织检查查不出来。
- 连接时复用密码登录拿到的访问令牌：现在紧接着会用刷新令牌再换一次，多一次请求。保存之前换出的新刷新令牌已经接住，不会存错（#118 审查）。
- 取值接口一次取多条时，同一个连接只读一次、几条凭据的条目并行取：现在逐条读连接、串行取（#119 审查；通常只取一两条，串行也不会同时压给密码库太多请求）。
- 官方服务（bitwarden.com）上没验证过的写入假设：修改时要带客户端版本头、`2026.10.0` 够不够新、名称与字段值的长度上限（读官方服务端的源码得来）、往只读集合新建时会不会悄悄建到集合外面。写入只在 Vaultwarden 1.37.4 上验证过（第 4 期审查）。
- 起标识时集合名从会话缓存的同步结果里取：集合只是改了名、id 还在缓存里时，响应里是旧名称，下一次同步之后才对（第 4 期审查）。
- 官方服务要求升级客户端时的拒绝报成 `server_error`（文字单独说明），没有单独的错误种类（第 4 期审查）。
- 疑似明文的规则：`Authorization: Bearer` 后面没有固定前缀的令牌认不出；`password = config.password` 这类代码表达式、`api_key: read/write` 这类权限说明会误报，靠 `plaintext_ok` 放行。按访问密钥实际被拒的情况再调（决策 4 的可推翻条件）。
- 疑似明文在 SQL 里每次都跑正则（待处理条数、列表筛选、概览）：两万条、每条几十处「password:」写法的代码笔记要 1.8 秒，主要花在类型名的判断上。条数多起来时，改成写入时算好、存成一列（#121 审查）。
- 保存前转存只处理这次写进来的值：更早的版本里以规则当时认不出的写法出现过的同一个值，不从历史里抹掉（待处理里的转存会抹）。要做的话，修改请求得带上转存的值，由服务端在同一个事务里清历史（#121 审查）。
- Lore 计划里，导入时换过占位符、Lore 正文还是明文的已导入节点，照样提示「正文疑似包含明文凭据」，可 Kioku 里的记忆已经没有明文（第 3 期走查）。
- Lore 计划判断要不要取凭据的值（`hasConvertedImports`）在只读快照之外查，也没有索引：竞态时这条同步按读不到值跳过，重出计划就对（第 3 期审查，有意不改）。
- 管理界面「找到连接、只在连接可用时读条目」的那段，在 `CredentialDetail.vue` 与 `CredentialFormModal.vue` 各写了一份，抽成 `useVaultItems`（#118 审查）。
