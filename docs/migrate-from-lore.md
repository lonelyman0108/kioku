# 从 Lore 迁移

有两种做法，规则相同：管理界面（上传 Lore 的导出文件，或者填 Lore 的地址，见「在管理界面导入」），和命令行工具（直接读 Lore 的数据库，见「步骤」）。

导入只读访问 Lore，把节点写进 Kioku 的一个空间。可以重复执行：按 Lore 节点去重，导入过的不再写入，导入后在 Kioku 里删除或移动了的也不会被写回；坐标已被别的记忆占用时跳过，计划里就列出来。所以先导一次、在管理界面里调整，再补导 Lore 里新增的节点都没问题。迁移期间两边可以并行，各客户端确认后再逐个切过来。并行期间在 Lore 里改过的节点，加 `--sync` 执行就能带过来（见「同步」）。

## 映射规则

| Lore | Kioku |
|---|---|
| `core://agent` | 通用 `core://agent`，所有应用都读 |
| `core://soul` | 人格 `persona://<人格>/soul`，默认人格标识 `default`，不存在而这次又要写入新的 soul 时新建 |
| `core://agent/<runtime>` | 导入者自己的对应应用 `app://<应用>/agent`。先找标识相同的应用，再找同一运行时类型的应用，都没有就新建；别的成员的应用不写，同名标识已被别人占用时跳过并说明 |
| `core://` 下的其他节点 | 通用，坐标不变 |
| `preferences://<路径>` | 导入者的本人 `user://preferences/<路径>`，敏感级内部（开启「本人私聊时读取本人记忆」后本人私聊也能用） |
| 其余的 `<分区>://<路径>` | 导入者的本人 `user://<分区>/<路径>`，敏感级私密 |

标题取 Lore 正文的第一个 `#` 标题，没有就用坐标的最后一段；标成机密的只用最后一段，不从加密的正文里取。

- 优先级（`priority`）、触发场景（`disclosure`）、关键词（`glossary`）保留，创建时间沿用 Lore 的。关键词按接口规则过滤：单字的丢弃，每条最多 32 个，超出时保留较长的。
- 新建的应用和原本没有默认人格的应用，默认人格设为导入的人格，与 Lore 里所有客户端共用 `core://soul` 一致。这次不写入新的 `core://soul`（Lore 里没有、之前导入过，或者界面上勾掉了）时不建人格；人格已经存在就照样用它，不存在时新建的应用默认人格为空。要新建的应用没有写入目标（节点都被跳过或勾掉了）时不建，不留空应用。
- 历史版本不迁移：每条记忆记一条 `import` 事件，带上 Lore 的节点 uuid 和旧版本数。Lore 的库留作归档。召回事件也不迁移。
- Lore 的别名（同一节点的多条路径）只导入最早的一条，其余在计划里列出。

## 明文凭据

Lore 里常有直接写在正文里的密码与令牌。Kioku 里推荐把值放进凭据，正文只留占位符 `{{cred:<标识>#<字段>}}`：agent 用 `kioku run` 取值，值不进对话，取用留有访问记录。

1. 导入之前先在「凭据」页把值备好：已经在密码库里的，在「凭据 › 密码库」里给条目起标识；不在密码库里的，新建一条凭据（连接设了去处时写进去处的集合，没有时由 Kioku 托管）。
2. 用管理界面导入。疑似明文按值和导入人已有的凭据比对：托管的，以及已对应到条目字段的密码库凭据。对得上的那一处，计划里写「与凭据「名称」`标识#字段`同值」，默认勾着「写成占位符」，写入时换成占位符；写入时还会核对它仍等于这条凭据这个字段现在的值。比对时不可用的连接、读不到的托管凭据，计划里给出个数。
3. 这几种照原样写，计划或结果里写明原因：
   - 目标放不进占位符：占位符只能放在本人、敏感级不低于私密的记忆里，导入为通用（`core://`）或本人 · 内部（`preferences://`）的不换；
   - 值也出现在坐标、标题、触发场景或关键词里；
   - 值太短；
   - 写入时凭据的值已经变了。
4. 已导入的节点只同步、不换，同步后可以在记忆详情或待处理里转存为凭据。
5. 对不上的，导入为机密，或者照原样导入后到「待处理 › 疑似明文凭据」里逐条转存为凭据（和密码库的条目按值比对，对上了可以当场起标识；对不上的新建一条凭据），规则误判的标「不是凭据」。

命令行导入不换占位符，只在计划的「提醒」里列出这些节点。

## 在管理界面导入

在「设置 › 空间 › 导入与导出」里操作，要空间所有者。

1. 选来源：
   - **上传导出文件**：在 Lore 的设置页导出（`GET /api/backup?action=export`），导出时不要带召回事件。文件在浏览器里先裁到导入要用的五张表，Lore 的 `app_settings`（里面有接口的 API Key）、事件与 dream 日记都不上传，废弃版本也不带正文。
   - **从地址拉取**：Lore 的地址与 API Token，由服务端去拉，要实例管理员。API Token 不保存；地址里不能带账号密码、查询与片段。Lore 要从 Kioku 的服务能访问到。
2. 看计划：每个节点写到哪、是新建还是已导入，同步差异，不含正文。目标坐标已被别的记忆占用的节点列在「不导入」里，计划里新建的条数就是会写入的条数。标出会进入启动加载的节点、正文引用的凭据、疑似含明文凭据的节点；疑似明文和已有凭据同值的，写明和哪条凭据的哪个字段相同（见「明文凭据」）。这些内容会按受信来源写入，所以只导入自己导出的文件。
3. 勾选：标记机密（已导入的节点不可勾选，要到记忆详情里改）、这次不导入（已导入的节点就是这次不同步），或者把和已有凭据同值的那一处写成占位符（默认勾着）。
4. 确认。执行时会重新读来源、重新算计划，和看过的不一致就要重看，勾选保留。文件比这个空间已写入的数据旧时，同步会把正文改回去，所以要单独确认。写到一半失败时已写的留着，重看计划接着来就好。

不要和命令行工具同时执行：界面的名额挡不住命令行，两边可能撞上同一个坐标。

## 步骤

1. 在管理界面完成初始化，确认导入用的账号是空间所有者。要导入机密记忆时，服务端必须配置了 `KIOKU_MASTER_KEY`。
2. 先看导入计划，不写入任何数据。计划先给新建、已导入、Lore 里换了路径、不导入各几条，再分组列出每条的标题、坐标（后面是 Lore 的 URI）、归属、敏感级与优先级；已导入的只给条数，加 `--verbose` 逐条列出：

   ```bash
   export DATABASE_URL=<Kioku 的连接串> LORE_DATABASE_URL=<Lore 的连接串> KIOKU_MASTER_KEY=<与服务相同>
   node apps/server/dist/import-lore.mjs --account <用户名> --secret infra://office_network/credentials
   ```

   用 Docker 部署时在服务容器里执行，Lore 的库要能从容器里访问（例如 `docker network connect` 把服务容器接到 Lore 所在的网络）：

   ```bash
   docker compose -f docker-compose.example.yml exec -e LORE_DATABASE_URL=<Lore 的连接串> \
     kioku node server/dist/import-lore.mjs --account <用户名>
   ```

3. 检查计划里的「提醒」：路径、正文、触发场景或关键词里疑似有密码、令牌的节点会列出来。命令行不会把值换成占位符，要换就用管理界面导入（见「明文凭据」）。也可以标为机密（`--secret <Lore 的 URI>`，可重复，对已导入的节点不生效）：正文加密存储，召回和启动加载都不再返回它，只有最高敏感级为机密的访问密钥显式读取时才能看到。节点里大部分是普通说明时，更合适的做法是照原样导入，再到「待处理 › 疑似明文凭据」里转存为凭据，正文只留占位符。
4. 确认无误后加 `--apply` 执行。导入完成后会安排一次向量补齐，服务正在运行时由它的后台任务接手。
5. 在「应用」里为要接入的应用签发访问密钥，按 README 接入客户端。

## 同步

导入过的节点在 Lore 里又改了，加 `--sync` 再执行一次（先不加 `--apply` 看计划）：

- 正文、标题、优先级、触发场景与关键词改成 Lore 里现在的，每条记一条「同步导入」事件。标题和导入时同一个取法，按现在的正文再取一次：Lore 里改了第一个 `#` 标题，同步后标题跟着改。敏感级不跟着改：要改成机密或从机密改回来，在管理界面里改。
- 只更新导入（或上次同步）之后在 Kioku 里没人改过的记忆：版本号还是导入工具最后写下的那个。在管理界面或通过访问密钥改过、移动过、删除了的都不动，只在计划里列出来，要跟上 Lore 就手动改。所以做过凭据迁移的节点不会被 Lore 里的明文盖回去。
- Lore 里换了路径的节点也只列出来：移动可能改变归属（例如移进 `core://` 就成了所有应用都读的通用记忆），要在管理界面手动移动；移动之后这条就算在 Kioku 里改过，以后要手动更新。换了路径之后映射到别的应用或归属的（例如从 `core://agent/<runtime>` 移到 `core://`），重新导入时也不会在新位置再建一条，结果里会列出来；加不加 `--sync` 都一样。
- Lore 里删掉的节点只列出来，Kioku 里保留。还在 Lore 里、但这次的计划不导入的节点（例如正文清空了、写进了格式不对的占位符），列出来并给出原因。
- 计划之后、执行之前有人改了某条记忆，执行时按版本号拒绝这一条，其余照常。
- 导入过机密记忆时，同步要读出来比对，需要设置与服务相同的 `KIOKU_MASTER_KEY`。
- 转存过凭据的记忆：Lore 里通常还是明文。同步时先按凭据现在的值把 Lore 正文换回占位符再比较，明文不会写回 Kioku。凭据换过值、或者 Lore 里删掉了这一处时，这条记忆不同步，计划里写明出路：值换过的，在 Lore 里也换成占位符；删掉的，在 Kioku 里同样删掉这个占位符（改过之后这条记忆不再随 Lore 同步）。凭据读不到值（删了、密码库不可用）时也不同步。
- 命令行和管理界面不要同时导入同一个空间：管理界面同一时间只做一次导入导出，挡不住命令行。两边同时写时，后写入的一方可能把对方刚写下的记为坐标已被占用。管理界面看过计划之后，这份计划里的节点又被别处导入了，会要求重新查看计划。

## 对照检查

导入后在管理界面的「测试台」里选 Claude Code 应用的访问密钥，发一次 `session.start`（默认回滚，不留痕迹）：

- 「结果中的 URI」里应当有与 Lore 启动时相同的四个节点：`core://agent`、`persona://default/soul`、`app://<应用>/agent`、`user://preferences/user`。
- 「收到的原文」里不应当有「未展开的启动节点」这一节（服务端输出的标题），结果里也不应当出现「超出预算、未展开的节点」。

不要用 `GET /v1/boot` 看：它的字数预算是 16000 字，而 Claude Code 的钩子只有约 7000 字（客户端上限减去指引与预留）。四个节点加起来超过这个数时，`/boot` 显示齐全，真实会话里排在后面的只剩一行坐标。

再用调用台发几句 `prompt.submit`，试试 `kioku_search`、`kioku_get`，看召回的是不是想要的；配了抽取模型的话，「模型对话」能用真实模型跑一段，看它会不会按指引调工具。没有配置嵌入模型时召回只走全文与关键词两路，在「设置 › 实例 › 模型」里配好嵌入接口后会补齐向量。
